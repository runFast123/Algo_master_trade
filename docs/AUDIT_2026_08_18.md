# Full system audit — 18 August 2026

Six parallel audits, one per subsystem: order lifecycle, market data, money
movement, frontend, sockets/session, and the strategy engine. Every finding
below was re-verified by hand against the code before being acted on.

Result: **462 Python tests, 392 UI checks, 45 against the compiled binary,
0 failures.** Up from 403 / 385 / 45 at the start. Every finding from all
six audits is now fixed.

The audit found more than the recent work. Several of the worst faults were
long-standing and had been passing every test suite this project has.

---

## Fixed

### 1. A network timeout could send an order — or a withdrawal — twice
`engine/app/choice_gateway/client_manager.py`

`TimeoutChoiceClient.request` retried on any `RequestException` or 5xx, for
**every** HTTP method. Choice's POSTs carry no idempotency key, so a read
timeout on `NewOrder` sent a second order and a timeout on `ProcessPayout`
booked a second withdrawal. A timeout is *"we do not know"*, not *"it failed"*
— the request may already have been accepted when the response was lost.

Now only `GET` is retried. This costs a retry on Choice's handful of read-only
POSTs (MultipleTouchline, GetDISStatus, CheckVPA, OrderMessages); losing a
retry on a quote is a refresh, gaining one on an order is a duplicate
position, so the trade is not close.

### 2. The kill switch reported success while every order stayed live
`engine/app/choice_gateway/orders.py`

`unwrap_list()` returns `[]` for a `{"Status":"Fail"}` envelope exactly as it
does for a genuinely empty book, and `cancel_all_open` never checked. A
refused order-book fetch — an expired session, a missing entitlement —
became "no working orders", and the halt returned
`{"cancelled": 0, "failed": 0, "status": "SUCCESS"}`.

The one moment the platform must not be optimistic. Now via
`_order_book_rows()`, which raises on a failure envelope and distinguishes it
from a real empty book. Every other gateway module already did this; orders
was the only one that did not.

### 3. An unrecognised order status was silently treated as finished
`engine/app/choice_gateway/orders.py`

`OPEN_STATUSES` was an exact-match allowlist over broker status strings that
have **never been verified** — the live order book has only ever come back
empty. Any wording Choice used that was not on the list read as terminal, so
the kill switch skipped the order without a word.

Inverted to a terminal-word list, so an unknown status is assumed *still
working*. Trying to cancel a finished order fails loudly; skipping a live one
does not. `PARTIALLY EXECUTED` is special-cased ahead of `EXECUTED` — the
unfilled remainder is still at the exchange.

### 4. A rejected order was recorded as accepted
`engine/app/choice_gateway/orders.py`

`place_order` — the one function that spends real money — hand-rolled its
failure check instead of calling `is_failure()`:

```python
str(response.get("Status", "Success")).lower() in {"failure", "fail", "error"}
```

An exact-cased key, defaulting to **success**, over a set missing `"false"`.
A lowercase `status` key or a `"false"` status meant a refused order was
recorded `ACCEPTED`, audited as placed, and reported as filled. The trader
believed they held a position they did not have.

### 5. Every lettered SELL order was uncancellable
`engine/app/choice_gateway/orders.py`

`bs=pick_int(row, "BS", "BuySell", default=1)`. `pick_int` goes through
`pick_float`, so `"S"` cannot be parsed and falls to the default — describing
a working SELL as a BUY. Choice refuses that, so those orders could not be
cancelled at all, including by the kill switch. This codebase's own
`_normalize_side` documents that Choice sends `"B"`/`"S"`.

Now `_side_code()`, which reads letters and numbers and **refuses** rather
than defaulting when the side is unreadable.

### 6. The diagnostic disclosed the account's entire holdings list
`engine/app/choice_gateway/normalize.py`, `backend/app/api/v1/diagnostics.py`

Two separate leaks, both active with `include_values=false`, in a report whose
own hint invited the reader to share it:

- `normalized` returned real balances and holdings regardless of the flag
- `describe_shape` and `flat_fields` emitted dict **keys** verbatim — and
  Choice keys its holdings payload **by ISIN**, so the "shape" was the
  holdings list under another name

An ISIN names a security exactly. Fixed by `is_keyed_collection()`, which
distinguishes a record (keys are field names, values are scalars) from a
collection keyed by data (keys carry digits, values share one schema). Field
names survive; identifiers are replaced by a count.

### 7. Paper trading filled at prices that were up to 89% wrong
`engine/app/choice_gateway/market.py`, `engine/app/choice_gateway/orders.py`

Reported in full in `API_SURFACE_AND_GAPS.md`. The audit found the first fix
had **two holes**, both now closed:

- `_market_fill_price` caught the deliberate refusal and filled at the
  caller's own submitted price instead — the same invention through a
  different door. It now lets `ChoiceGatewayError` propagate, and refuses a
  market order outright when no price can be obtained.
- The fill was stamped `price_source: "live_ltp"` whenever the session had
  broker credentials, regardless of where the price actually came from, and
  the user was told "filled at the live price" for a Friday-close snapshot.
  Provenance now comes from the quote, and the message names it honestly.

Also fixed: a holding Choice never priced was published as a quote that had
traded exactly flat (`priced_from_close` was ignored), and quotes were sourced
from holdings only — so every instrument the account did not own became
un-paper-tradable. Positions are now consulted too.

### 8. Non-finite and absurd transfer amounts reached the payout endpoint
`engine/app/choice_gateway/funds.py`

`nan <= 0` and `inf <= 0` are both `False`, so both passed the positivity
check. Python's JSON parser accepts the bare `Infinity` and `NaN` literals, so
both could reach `ProcessPayout` — and the confirmation dialog would have read
"Rs inf". Now rejected, with a `MAX_TRANSFER` ceiling as well.

## Fixed in the second pass

### 9. Every order shared one client order number
`engine/app/choice_gateway/orders.py`

The SDK hardcodes `"ClientOrderNo": 123456` on every `NewOrder`
(`choice_api/orders.py:27`). Cancellation finds an order by that field, so two
live orders meant a Cancel on one could withdraw the other, and reconciliation
collapsed the whole book into a single bucket.

Placement now builds its own payload through `client.request` with a unique
number from `next_client_order_no()`. For orders already at the broker under
the old shared number, `cancel_one` matches on any of the three identifiers
and **refuses when more than one row matches** rather than picking the first —
ambiguity is reported, never resolved by guessing.

Fixed alongside: the placement reply was read from the raw payload rather than
through `unwrap_dict`, so `order_id` came back empty and every live order
looked `missing_at_broker` to reconciliation, permanently.

### 10. The per-order value cap did not apply to market orders
`engine/app/choice_gateway/orders.py`

`order_value = quantity * price`, and a market order carries `price = 0`, so
the Rs 500,000 cap never applied to the one order type with no price ceiling
of its own. `validate_order` now takes a `reference_price`, resolved from a
quote for market orders. When no price can be had the quantity cap still
applies and the gap is logged — a quote outage must not become an inability to
trade.

### 11. A mode switch did not survive a restart
`engine/app/choice_gateway/client_manager.py`, `backend/app/services/auth_service.py`

Only login persisted the session, so switching LIVE to PAPER left `"LIVE"` on
disk. `restore()` is reached automatically from `GET /auth/choice/status`,
which the UI calls on load — so a user who chose paper could be put back into
live silently, bypassing the confirmation that guards that direction. Both
paths now go through `ChoiceSession.persist()`.

### 12. The kill switch did not stop a running paper strategy
`engine/app/strategy_engine/runner.py`

The runner's PAPER branch built its fill dict directly and never called
`orders.validate_order`, so it never reached the risk manager at all. A halt
stopped manual paper orders while a paper strategy carried on entering and
exiting; the paper loss cap could never trip from a run; and neither the
notional nor the quantity cap applied to a strategy's own orders.

The branch is now validated like any other order, and realised losses are
booked to the paper ledger. Scope is preserved: a `scope="real"` loss-cap halt
still leaves paper work running.

### 13. Backtests could run on a US-listed instrument in dollars
`engine/app/choice_gateway/marketstack.py`

The symbol candidate list ended with the bare ticker. Marketstack resolves a
bare `INFY` to the New York ADR at about **$11.62** rather than Infosys at
**Rs 1,139.90**, and `IEX` to Idex Corporation — a different company. Every
backtest on this account uses Marketstack, because Choice's historical
endpoint is dead. The bare candidate is gone, and `_foreign_listing()` now
checks the `price_currency` the rows already carried and skips any non-INR
match.

### 14. A quote in a strategy name broke every button on its row
`frontend-user/index.html`

`esc()` escapes for HTML, but the HTML parser decodes an attribute *before*
the handler is compiled as JavaScript — so an escaped quote came back live and
closed the string. A strategy named `Kunal's momentum` silently disabled Open,
Duplicate, Backtest and Run paper on that row; a name chosen deliberately
could run anything. Strategy names are free user input, so this was reachable.

New `jsq()` escapes for JavaScript first, then for HTML. Verified by mutation:
reverting one call site to `esc` fails the new check with the literal broken
handler `startRun('s1','Kunal's momentum')`.

## Fixed in the third pass — the platform's own books

One theme: what the platform records had come apart from what actually
happened.

### 15. The daily loss cap was updated by a display poll
`backend/app/services/order_service.py`

`risk_manager._realized` — the ledger the real-money cap is enforced against —
had exactly one writer: `funds.get_funds`, reachable only from
`GET /portfolio/funds`, which only the dashboard calls. So the circuit breaker
advertised on the Health panel and by `/orders/limits` depended on somebody
having the page open. Trading through the API, or with the dashboard closed,
left it at zero however much was lost.

`refresh_realized_pnl()` now runs after every real fill. Best effort by
design: it runs after the order is already placed and recorded, so a funds
call that fails cannot turn a successful order into an error.

### 16. Amend and cancel never touched the local order record
`backend/app/api/v1/orders.py`

The local book is what the interface, the CSV export used for accounting and
reconciliation all read. An order placed at 10 @ 2400, amended to 200 @ 2500
and then cancelled still reported **10 @ 2400, ACCEPTED** forever — and
reconciliation could not see the divergence either, because it treats a local
`ACCEPTED` as compatible with any broker status.

Both routes now update the row through `_local_order()`, which matches on
either the client or the exchange number and is **tenant-scoped**, so a
colliding order number cannot be used to rewrite another account's book. No
local record is a valid answer rather than an error — an order placed from the
Choice website has no row here, and cancelling it must still work.

### 17. Money moved with no audit trail
`backend/app/api/v1/portfolio.py`

Orders, logins, mode changes and role changes were all audited. Withdrawals,
deposits and position conversions were not — the only trace was a log line
written *before* the call, so it existed even when the payout was refused and
there was no record at all when one succeeded. A disputed payout had nothing
naming the actor, the amount, the destination or the time.

Now `FUNDS_WITHDRAWN`, `FUNDS_DEPOSIT_STARTED` and `POSITION_CONVERTED`, with
`FUNDS_WITHDRAWAL_REFUSED` on the failure path too — a run of refusals is what
a compromised token looks like.

## Fixed in the fourth pass — data accuracy and the ticket

### 18. The instrument master never loaded on most sessions
`engine/app/choice_gateway/scrip_master.py`

The SDK loads its scrip master CSV inside `ChoiceClient.login()` and nowhere
else. Three of the four ways a session is established — `validate_totp`,
partner OAuth, and `restore` on every restart with "remember me" — build the
client directly and never call it. On those sessions instrument search
returned nothing and **every lot size came back as 1**, which silently
disables the multiple-of-lot check for all F&O.

Now loaded lazily on first use, and `get_lot_size` returns `None` rather than
1 when it cannot be established. The difference matters: 1 means "trades in
single units" and waves any quantity through; `None` means "unknown" and the
interface can say so.

### 19. Amending could silently remove a protective stop
`engine/app/choice_gateway/orders.py`, `frontend-user/index.html`

`_normalize_order` defaulted a missing `order_type` to `RL_LIMIT` and
`product_type` to `CNC`. Those field names are unverified — the live order
book has only ever come back empty. If Choice names them differently, a
working `SL_LIMIT` stop normalised to a plain limit: the amend dialog then hid
the trigger field and posted `trigger_price_in_paisa: 0`, so a user changing
only the quantity **deleted their own stop-loss** and nothing said so. The
`CNC` default did the same to an MIS order, converting intraday to delivery.

The defaults are gone. `canAmend()` withholds the Amend action when the book
does not report enough of the order to resend it unchanged, and `openModify`
refuses too — the button is not the only way in.

### 20. A flat price series read as maximally oversold
`engine/app/strategy_engine/dsl.py`

With no gains and no losses, the two `.where` clauses were ordered so the
second overwrote the first and RSI came out **0** — identical to a collapse.
An `rsi < 30` entry, the most common strategy in this product, fired on every
flat bar; and a stale repeated price produces exactly such a series. Flat is
now 50. Verified across all four cases: flat 50, rising 100, falling 0, and
the warm-up NaNs preserved.

### 21. Backtests were silently truncated to the plan's history
`engine/app/choice_gateway/marketstack.py`, `backend/app/services/strategy_service.py`

A 3.6-year request returned 1.0 year and reported success, with Sharpe, max
drawdown and win rate all computed over a period nobody asked for. The
provenance now carries the window actually covered, the service persists it
rather than keeping only the source name, and the backtest page states it
above the metrics.

### 22. The order ticket discarded the instrument's segment
`frontend-user/index.html`

A token is unique only *within* a segment: 2885 in segment 1 is Reliance
equity, in segment 2 an unrelated derivative. The search dropped the segment
and the order took it from a dropdown defaulting to NSE Cash — so picking an
F&O contract and leaving the dropdown alone sent an F&O token against the cash
segment. The instrument's own segment now wins, and the ticket says so when
the two disagree.

### 23. The fat-finger guard was absent when it was most needed
`frontend-user/index.html`

The large-order confirmation is gated on order value, and for a market order
the price came only from `state.holdings`. Buying something not already held
left the value at 0 and skipped the confirmation entirely — the control built
for a mistyped quantity, missing precisely when the instrument is unfamiliar.
It now falls back to the costing preview's price, and when no price exists at
all it questions the quantity instead of checking nothing.

### 24. Paper runs ignored costs the backtest applied
`engine/app/strategy_engine/runner.py`, `engine/app/costs.py`

The paper runner booked `(price - entry) * qty` with no slippage and no
charges, while the backtest applied both to the same bars. On 200 round trips
of 100 shares at 500 that is **about Rs 39,400 of delivery costs** the paper
run never subtracted — enough to turn a losing strategy into a winning one on
screen, which is the number someone would promote to live on.

Paper runs now use the same `CostModel` the backtest does.

Fixed with it: `CostModel` always applied the **delivery** schedule, so an
intraday preview charged STT on the buy leg (which does not exist for MIS) and
at four times the rate. `for_product()` selects the right schedule, the
preview request carries the product, and changing the product re-prices the
ticket.

## Verified clean

Stated because they were suspected and checked, not assumed:

- **Price scaling.** `LTP` and `ClosePrice` are scaled ints sharing
  `PriceDivisor`; confirmed against the captured production fixture across
  seven instruments including ₹1.82 and ₹1000.00 edge cases. No 100x bug.
- **No simulated session can move real money.** `_require_real_session`
  precedes `require_client()` and the network call on every path.
- **The `uses_broker_data` widening of the price-feed gate is safe.** Exactly
  one session state was added — PAPER with a session id — and DEMO still
  cannot pass despite carrying a synthetic session id.
- **`risk_manager`'s paper/real isolation is correct**: a paper loss cannot
  halt real trading, and `_roll_day` is race-free.
- **Paisa rounding** in the frontend: `Math.round` absorbs the float error at
  every call site.
- **`RunRegistry`** has no meaningful leak, and a RUNNING run cannot be pruned.
- **PAPER→LIVE cannot turn a paper strategy into real orders** — a
  `RunMode.PAPER` run never touches the order gateway at all.
